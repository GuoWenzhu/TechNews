## 1. Google Project Zero 修改漏洞披露政策：报告后 90 天无条件公开，2028 年压缩到 30 天

- **发布时间**：2026-11-14（Project Zero 官方博客，2026/11 目录；HN 讨论 11-14T11:13Z 起 130 分）
- **来源**：Google Project Zero 官方博客（一手）；Hacker News 讨论
- **核心内容**：Project Zero 自 2021 年起实行"90+30"政策（厂商 90 天修复期 + 30 天补丁推广观察期），现改为"Full X"：漏洞报告给厂商后 X 天即公开细节，无论是否已修复。时间表：即日起 Full 90；2027 年 2 月 2 日起 Full 60；2028 年 1 月 3 日起 Full 30。同时取消大部分特例（宽限期、变体政策等），仅保留三个例外：在野利用漏洞（按 Google 应用安全披露政策处理）、已被他人公开的漏洞、厂商主动要求公开。调整理由：(1) LLM 加快了攻击者发现和利用漏洞的速度，"补丁发布到武器化"的时间趋近于零，观察期已无意义反而制造虚假安全感；(2) AI 辅助使 P0 的漏洞报告量从"每年几条"增至"每周几条"，需要人工协商的环节（确认是否修复、是否适用宽限）不可维系；(3) 新政策目标是促使厂商加快修复、压缩"补丁缺口"（patch gap，即修复发布到用户装上的时间差），且规则可被双方自动化执行。是否修复仍会跟踪，但不再作为披露决定点。
- **背景/影响**：本周 Apache HTTP Server 关键 RCE 刚由 Anthropic OSS Scanner 与 Google Cloud 团队独立发现，AI 辅助漏洞挖掘进入实战产能阶段；P0 此番把"披露倒计时与修复进度脱钩"制度化，等于宣布 AI 时代漏洞生命周期全面提速。对厂商与运维团队：安全补丁窗口预期将从 90+30 天一路压缩到 30 天，补丁发布流程、非补丁缓解手段（关路径、特性开关）与灰度回滚机制需要按新节奏重排。

## 2. 对 15.9 万个 Lovable 应用的审计：30% 被深入检查的应用数据库未登录可读，护照号与 20 万条聊天记录暴露

- **发布时间**：2026-11-14（Crissyfield 研究报告；Handelsblatt 首报 2026-11-02，本报告为其更新版；HN 讨论 11-14T17:43Z 起 586 分）
- **来源**：Crissyfield 研究报告（一手，与 Handelsblatt 合作）；Hacker News 讨论
- **核心内容**：德国安全公司 Crissyfield 与《商报》（Handelsblatt）合作，基于 Common Crawl 识别并分析 159,041 个 Lovable（AI 应用生成平台）项目（2025-12 至 2026-09），其中 34,545 个使用 Supabase 数据库。发现：24,664 个站点在首屏加载、无需登录时即返回数据库记录；对其发起进一步只读请求后，7,403 个站点（占深入检查样本的 30%）的 10,560 张表含邮箱地址等个人数据可直接读取。典型案例：德国某生活论坛暴露 8 万+ 用户档案（全名/邮箱/生日/性别）与 20 万+ 条聊天消息；某服务商暴露 1,000+ 条身份证件记录（护照号、有效期、国籍）；多个活动与餐饮商家暴露数万条订单（含支付信息与票码）；某物业管理公司暴露含租户敏感信息的内部邮件 AI 摘要；某案例中 28 万封发给客户的邮件可读。根因是 Supabase 行级安全（RLS）配置错误的重复模式——Lovable 的数据库集成遵循相似模板，一种攻击手法可批量套用于多个应用；平台条款将数据安全责任归于用户。报告明确限制：30% 不是确认的泄露率，样本来自 Common Crawl 不代表全部应用；未公开访问方法以免扩大暴露。
- **背景/影响**："零代码基础也能上线真实应用"的安全债首次被大规模量化：AI 生成代码 + 模式化第三方集成 + 非技术用户三者叠加，使单点配置错误放大为平台级批量风险。对 AI 应用落地团队，这是对"上线前人工安全审查（权限、接口、账号隔离）不可省略"的直接提醒；对平台方，责任条款与模板化集成的组合是结构性问题，自动化检查不能替代专业安全评估。

## 3. ggml 发布首个 1.0 稳定版：llama.cpp 底座进入 API 稳定期，FP8 与全后端性能更新

- **发布时间**：2026-11-13 08:34 UTC（GitHub Release v1.0.0；HN 讨论 11-14T02:28Z 起 398 分）
- **来源**：ggml-org 官方 GitHub 仓库（一手）；Hacker News 讨论
- **核心内容**：本地推理事实标准 llama.cpp 背后的张量库 ggml 发布 1.0.0——项目首个语义化稳定版本。API 层：清理全部弃用公共 API 与遗留 DIAG_MASK 算子，RPC 协议升至 v9 并拒绝不兼容对端，新增 `ggml_rope_set_truncate`/`get_truncate`（YaRN 截断控制）。量化与数值：新增 OCP FP8 支持与 FP8 KV cache、NVFP4 gate/up 矩阵乘与 GLU 融合、可配置 YaRN 截断。性能工作覆盖全部后端：CUDA/Metal 的少行量化矩阵乘与 MoE 融合路由（含 DeepSeek-V4/V4.1、GLM MoE 路由融合）、Vulkan 的 Intel prefill FlashAttention 内核与 AMD 大分片 split-K、SYCL 设备端 MoE 调度、OpenCL 的 Adreno（安卓 GPU）分解 FlashAttention、新增 WebGPU 内核、Hexagon（骁龙 NPU）算子扩展、CPU 端 F32 累加与 NEON 4x4 分块等。调度器不再上传未被读取的输入、只预取前序切分产物。
- **背景/影响**：ggml 是端侧与消费级硬件 LLM 推理的公共底座，1.0.0 的 API 冻结承诺直接改善下游运行时与应用的集成稳定性；FP8/NVFP4 与 MoE 融合等改动会顺着 llama.cpp 传导到本地部署的推理效率。对本地部署/微调实践者，这是继本周 Edge0 开源 145B 端侧模型后，本地推理基础设施的又一个标志性节点。

## 6. NVIDIA 教程：两台 DGX Station 经 RDMA 直连本地服务 753B 参数 GLM-5.3，并发 16 总吞吐 607.8 tok/s

- **发布时间**：2026-11-14（NVIDIA 开发者博客；HN 讨论 11-14T14:09Z 起 126 分）
- **来源**：NVIDIA 开发者博客（一手）；Hugging Face 模型页；Hacker News 讨论
- **核心内容**：NVIDIA 发布端到端教程：用两台 DGX Station（各一块 GB300、252GB HBM3e 显存）以 ConnectX-8 双轨 RoCE RDMA 直连，vLLM 张量并行（TP=2）跨两机服务智谱 Z.ai GLM-5.3 的 NVFP4 量化版。模型为 753B 总参数、每 token 激活 40B 的 MoE，checkpoint 约 464GB、50 个 safetensors 分片——单机 252GB 显存放不下全部权重，双机各载约 218GiB；单一 OpenAI 兼容端点对外服务。推理配置：MTP 投机解码（每步起草 4 个 token 由全模型验证）、FP8 KV cache、前缀缓存、vLLM v0.30.0。SPEED-Bench Coding 实测：并发 1 时单用户吞吐 115.3 tok/s（TTFT 约 480ms）；并发 16 总吞吐峰值 607.8 tok/s（逐 token 延迟约 24ms）；并发 32 过载回落至 385 tok/s。教程覆盖双机组网校验、RDMA 直通验证、AIPerf 压测与常见故障排查，模型权重为 HF 上的 nvidia/GLM-5.3-NVFP4。

## 8. Perplexity 开源决策模型 Decider v1.3：一次前向回答多个分类问题，生产分类任务准确率 91.6%

- **发布时间**：2026-11-13（Perplexity 官方博客；HN 讨论 11-13T19:24Z 起 144 分）
- **来源**：Perplexity 官方博客（一手）；Hugging Face 模型集合；Hacker News 讨论
- **核心内容**：Perplexity 发布 Decider v1.3 及其蒸馏版 Decider Flash v1.3（Apache 2.0，Hugging Face、OpenRouter 与 Decision API 可用），把生成式 LLM 改造成"决策模型"——通用分类器：输入一个共享 state 加若干问题（yes/no、多选、评分三类），单次前向即返回所有问题的概率分布，避免逐 token 生成。技术要点：基座 Qwen3.8-27B（Flash 由其蒸馏到 Qwen3.5-4B，KL 目标）；将全注意力层改双向、采用"隔离问题"注意力（state 可见所有问题、问题只看 state 与自身）以换取稳定性；三阶段训练（通用微调 → LoRA 领域化 → 视觉 LoRA），三种子权重平均；v1.3 新增 locate 能力，用 span 头返回 NER/PII/抽取式问答的文本片段与字符位置。评测：63 个生产查询分类任务平均准确率 91.6%，超现网产线分类器 6.54 个百分点；72 个检索重排任务 nDCG@10 83.99，超 Qwen3-Reranker-8B；对上线首 18 天的 100 万条真实 Decision API 请求（232 万个问题），与 frontier LLM 评审一致率 93.98%；标签重排下答案翻转率仅 0.27%（对比同类 Jev 1.14 的 2.69–4.84%）。内部用例：一天读完 10 亿 token、7000 个智能体会话日志自查安全规则盲区，产出 14 条规则修复（上线一周后最繁忙规则的处理量降 52%）；另用于监控 RL rollout 与爬取页面质量过滤。
